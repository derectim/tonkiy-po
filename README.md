# Тонкий По — концепт сайта бистро

Интерактивный прототип с согласованным направлением: современное азиатское бистро, сдержанная атмосфера и редакционная композиция. HTML/CSS/JS, не установленный WordPress.

## Визуальная система

Единая сцена общего стола, крупная антиква Cormorant Garamond, тёмный зелёный и тёплая слоновая кость. Типографический индекс меню и фотографии без промо-плашек. Функциональный текст от 14px. Применены MengTo design-first-ui-prompting, build-awwwards-quality-sites и cinematic-gsap-lenis-motion-system.

Движение: GSAP/ScrollTrigger 3.15.0; единственный smooth-scroll engine Lenis 1.3.26. На coarse pointer и reduced motion Lenis выключен. Диалоги и скрытая вкладка останавливают движение. Three.js не используется: пространственные эффекты не нужны этой композиции.

Изображение первого экрана создано встроенным image_gen для атмосферного концепта: dist/assets/editorial-table.jpg. Оно не является фотографией реального стола/интерьера кафе. Prompt сохранён в ../references/editorial-hero-prompt.txt. Фото 29 блюд, их цены и описания взяты с действующего pocafe.ru 15 октября 2026. Шрифты локальные OFL, иконки Solar с CC BY4.0 (атрибуция в assets/icons).

## Работающие сценарии

Категории и поиск по меню, детали блюда, избранное, корзина с пересчетом, доставка/самовывоз, адрес, демо-оформление, ручное переключение этапов, история и повтор заказа. Корзина/история хранятся локально, адрес только в текущей сессии. Два блюда с ценой «от» требуют уточнения вариантов в кафе и не добавляются с выдуманной ценой.

Прототип не отправляет заказ в кафе, не принимает платежи и не отправляет SMS. Сроки/стоимость доставки без подтверждения не выдуманы.

## Для рабочего сайта

Для одного кафе разумная стартовая архитектура — WordPress с собственной темой + WooCommerce + связь с системой кафе. Визуал переносится в тему; демонстрационную корзину/кабинет заменяют серверные.

Сначала нужно выяснить, куда сейчас приходят заказы и где сотрудники отмечают приготовление/выдачу. Затем проектируются синхронизация меню, цен, стоп-листа, заказов и статусов. При iiko/r_keeper источником статусов должна быть эта система; при ручной работе нужен интерфейс сотрудников. Трекер нельзя определять по таймеру. Геолокация курьера — отдельная интеграция.

Дополнительно нужны вход по телефону, платежи и серверные подтверждения, согласованные правила доставки и настройки администратора.
